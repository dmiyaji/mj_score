## 1. 試合一覧取得の N+1 クエリ解消（中）

- **対象**: `lib/database.ts` `gameResultOperations.getAll`
- **現状**: 試合ごとに `player_game_results` を 1 回ずつ取得している。100 試合なら 101 クエリになる。
- **改善案**: `game_results` と `player_game_results`・`players` を 1 回の JOIN で取得し、JS 側で試合ごとにまとめる。

**理由**: 試合数に比例してクエリが増え、Workers のサブリクエスト上限（無料枠 50）に達すると公開画面とエクスポートが 500 になる。

**メリット**

- 試合数が増えても、一覧とエクスポートが失敗しなくなる
- 応答時間が短くなり、D1 の読み取りも減る

**懸念点**

- 戻り値の形（`player_game_results` の並び順や `players` の JSON）を今と同じにする必要があり、画面側の確認が要る
- 全件を一度に返す仕様は変わらないため、将来的にはページングも検討が必要

---

## 2. ログインのレート制限（中）

- **対象**: `app/api/auth/login/route.ts`
- **現状**: 失敗回数の制限がなく、パスワードを総当たりで試せる。
- **改善案**: Cloudflare の Rate Limiting ルール（WAF）で `/api/auth/login` を制限する。コードで行う場合は Workers の Rate Limiting バインディングを使う。

**理由**: 管理者パスワード 1 つで書き込み権限のすべてを守っているため、試行回数に上限がないとパスワード強度だけが防御になる。

**メリット**

- 総当たり攻撃を実質的に防げる
- WAF ルールで行えばコード変更が不要

**懸念点**

- 管理者自身が入力ミスを繰り返すと一時的にロックされる
- WAF ルールはコード外の設定になるため、`docs/RELEASE.md` などに記録しないと構成が把握しづらい
- バインディングを使う場合は `wrangler.jsonc` の変更と `npm run types:cf` が必要

---

## 3. シーズン削除の制御（中）

- **対象**: `lib/database.ts` `seasonOperations.delete`、`app/api/seasons/[id]/route.ts`
- **現状**: 試合があるシーズンも削除でき、試合の `season_id` が NULL になる。アクティブなシーズンを消すと成績入力ができなくなる。
- **改善案**: 試合が 1 件でもあるシーズン、またはアクティブなシーズンの削除は 409 で拒否する。

**理由**: 誤操作 1 回で過去の試合がどのシーズンの集計にも出なくなり、元に戻すにはバックアップからの復元しかない。

**メリット**

- 誤削除による集計の欠落を防げる
- 「アクティブなシーズンがない」状態に陥らなくなる

**懸念点**

- テスト用に作ったシーズンを、試合ごと消したい場合に削除できなくなる（先に試合を消す手順が必要）
- 画面側で拒否理由をわかりやすく表示する対応が要る

---

## 4. 復元・取り込み時の `current_stage` の保持（中）

- **対象**: `lib/database.ts` `restoreFullDatabase`、`upsertTable`（seasons）、`parseCSV`（seasons）
- **現状**: seasons の INSERT に `current_stage` が含まれず、復元すると既定値の REGULAR に戻る。
- **改善案**: INSERT と `ON CONFLICT` の更新対象に `current_stage` を加える。値がないときは REGULAR とする。

**理由**: FINAL ステージ中にバックアップから復元すると REGULAR に戻り、以後の成績が誤ったステージで登録される。

**メリット**

- バックアップからの復元で、シーズンの状態を完全に戻せる

**懸念点**

- `current_stage` を含まない古いバックアップでは REGULAR になる（現状と同じ挙動のため悪化はしない）
- 値の検証（REGULAR / FINAL 以外を拒否する）も合わせて入れる必要がある

---

## 5. 試合結果の取り込みで id のない行をエラーにする（中）

- **対象**: `lib/database.ts` `upsertTable`（gameResults）
- **現状**: `id` のない試合は何もせずに読み飛ばすが、件数は入力件数のまま成功を返す。
- **改善案**: `id` のない行があれば、取り込み全体をエラーにして行番号を返す。または新しい id を振って登録する。

**理由**: 登録されていないのに成功と表示されるため、利用者が取り込み済みと誤解し、データの欠落に気づけない。

**メリット**

- 取り込み結果と実際のデータが一致する

**懸念点**

- 新しい id を振る方式だと、同じ CSV を 2 回取り込んだときに試合が重複する（エラーにする方式が安全）
- これまで一部の行だけ成功していた CSV が、全体としてエラーになる

---

## 6. CSV パーサの改善（低）

- **対象**: `lib/database.ts` `parseCSV`
- **現状**: 行を `\n`、列を `,` で単純に分割しているため、引用符で囲んだ値の中のカンマや改行を正しく扱えない。
- **改善案**: 引用符・エスケープ（`""`）・CRLF に対応したパーサにする。小さな自前実装か、`papaparse` などのライブラリを使う。

**理由**: エクスポートはカンマを含む値を引用符で囲むが、取り込み側はそれを分割するため、自分で出力した CSV を正しく戻せない。

**メリット**

- エクスポートした CSV をそのまま取り込める
- Excel で保存した CSV（CRLF）も扱える

**懸念点**

- ライブラリを使うと依存が増える（追加は `npx npm@10 install` で行う）
- パーサの単体テストを新たに用意する必要がある

---

## 7. CSV 出力で 0 を空文字にしない（低）

- **対象**: `lib/database.ts` `exportToCSV`
- **現状**: `value || ""` により、0 が空文字で出力される。
- **改善案**: `value ?? ""` にして、null と undefined だけを空文字にする。

**理由**: ポイント 0 やペナルティ 0 が空欄になり、表計算ソフトで集計したときに未入力と区別できない。

**メリット**

- 出力値が DB の値と一致する

**懸念点**

- 取り込み側は空欄を 0 として扱っているため互換性の問題はない。出力の見た目が変わる程度

---

## 8. 500 応答から内部エラーメッセージを除く（低）

- **対象**: `app/api/game-results/route.ts`（POST）
- **現状**: 認証不要の API が、例外のメッセージを `details` としてそのまま返している。
- **改善案**: アクティブなシーズンがない場合など、利用者に見せる想定のエラーだけを専用のエラー型で返し、それ以外は汎用メッセージにする。

**理由**: 誰でも呼べる API で D1 や SQL のエラー文が返り、テーブル名や制約名などの内部情報が外部に見える。

**メリット**

- 内部構造の露出を防げる

**懸念点**

- 画面に表示している「アクティブなシーズンがありません」などのメッセージを残す仕組み（専用エラー型など）が必要
- 障害調査ではログ（`console.error`）を見る必要がある

---

## 9. 統計 API の日付パラメータ検証（低）

- **対象**: `app/api/stats/players/route.ts`、`app/api/stats/teams/route.ts`
- **現状**: 不正な日付を渡すと `toISOString()` が例外を投げ、500 になる。
- **改善案**: `Number.isNaN(date.getTime())` で検証し、不正なら 400 を返す。

**理由**: 利用者の入力ミスがサーバーエラーとして扱われ、エラー監視のノイズになる。

**メリット**

- 原因がわかる応答を返せる

**懸念点**

- 特になし（正しい入力の挙動は変わらない）

---

## 10. アクティブなシーズンを常に 1 件にする（低）

- **対象**: `lib/database.ts` `upsertTable`（seasons）、`restoreFullDatabase`
- **現状**: 取り込みで `is_active = 1` の行が複数あると、アクティブなシーズンが複数になる。
- **改善案**: アクティブな行が 2 件以上ある入力は拒否する。または最後の 1 件だけをアクティブにする。DB 側の部分ユニークインデックス（`WHERE is_active = 1`）も検討する。

**理由**: `getActive` は `LIMIT 1` で任意の 1 件を返すため、成績がどのシーズンに登録されるかが定まらなくなる。

**メリット**

- 成績の登録先が常に一意に決まる

**懸念点**

- インデックスを追加する場合は新しいマイグレーションが必要。既存データにアクティブが複数あると適用に失敗するため、事前の確認とデータ修正が要る

---

## 対応の優先順位（案）

1. **#1 N+1 解消** と **#3 シーズン削除の制御**: データ量の増加や誤操作で実害が出やすい
2. **#2 レート制限**: WAF 設定ならコード変更なしで対応できる
3. **#4・#5・#10 取り込み・復元まわり**: まとめて 1 つの PR にすると確認しやすい
4. **#6〜#9**: 小さな修正のため、余裕のあるときに順次
